# 보안 정책

## 인증 흐름

1. 로그인 화면 `/uat/uia/egovLoginUsr.do`에서 업무사용자 탭을 고르면 폼이 `id`, `password`, `userSe=USR`, `_csrf`를 `/uat/uia/actionLogin.do`로 보낸다(공통컴포넌트 Spring Security 방식).
2. 로그인 필터가 먼저 잠금 정보를 본다(`Globals.login.Lock = true`, `Globals.login.LockCount = 5`).
   - 잠금 표시가 켜져 있으면 비밀번호와 관계없이 "잠금" 메시지로 거부한다.
   - 비밀번호가 맞으면 실패 횟수를 지운다.
   - 틀리면 실패 횟수를 1 올리고, 5회째에 잠금 표시를 켠다.
3. 공통컴포넌트 로그인 SQL은 업무사용자 상태가 승인(`P`)인 계정만 찾는다. 이어서 Spring Security가 권한 행(한 사용자당 1행)을 읽는다. 권한 행이 없으면 사용자를 찾지 못한 것으로 실패한다.
4. 성공하면 세션이 만들어지고 `/EgovContent.do`로 간다. 세션 쿠키는 `Secure; HttpOnly`다. 평문 HTTP에서는 브라우저가 `localhost`에서만 쿠키를 보낸다.
5. 동시 세션은 1개(`concurrentMaxSessons = 1`)이며, 로그아웃은 `/uat/uia/actionSecurityLogout.do`다.

비밀번호는 공통컴포넌트 방식 `EgovFileScrty.encryptPassword(비밀번호, 아이디)`(아이디를 솔트로 쓴 SHA-256 1회, Base64)로 저장한다.

## 역할과 권한

역할 계층: `ROLE_USER` → (`ROLE_ASSET`, `ROLE_ADMIN`). 두 역할 모두 `ROLE_USER`의 하위다. `ROLE_ASSET`과 `ROLE_ADMIN`은 서로를 물려받지 않는다.

URL 권한은 DB(`COMTNROLEINFO` 정규식 패턴 + `COMTNAUTHORROLERELATE`)에 있다. 패턴은 정렬 순서(`ROLE_SORT`, 문자열 비교)로 평가되며 **처음 일치한 패턴이 결정한다**. 같은 정렬 값끼리의 순서는 정해져 있지 않다. 업무 패턴은 `'0'`, 공통컴포넌트 관리 영역 차단 패턴은 `'05'`라서, 공통컴포넌트의 회원관리(`'1'`)와 모든 `.do` 포괄 패턴(`'3'`)보다 먼저 평가된다. 공통컴포넌트는 로그인 사용자 모두에게 포괄 패턴으로 모든 `.do`를 열어 두므로, 관리 화면은 이 차단 패턴이 없으면 신청자에게 열린다(예: 부서권한관리로 자기 권한을 관리자로 바꾸는 요청). 권한 없는 접근은 거부 화면(`/sec/ram/accessDenied.do`)을 받는다.

|---|---|---|---|
| `/asset/req/**` 신청 작성·내 신청·취소 | 허용 | 허용 | 허용 |

마지막 줄에는 이 시스템이 메뉴로 쓰지 않는 공통컴포넌트 전시용 기능(커뮤니티·동호회·설문·일정·지식관리·뉴스 등 `/cop/**`, `/dam/**`, `/uss/ion/**`의 나머지, `/uss/olh/**`, `/uss/olp/**`)이 포함되어 로그인 사용자 누구나 URL로 열 수 있다. 계정·권한·업무 데이터(품목·재고·자산·신청)에는 닿지 않는다.

서비스 계층에서 한 번 더 막는 것(URL만으로는 부족한 규칙):

- 승인·반려: 신청자 본인이면 거부하고, 지금의 승인자(부서장/관리자 규칙)가 아니면 거부한다. 모든 경로가 같은 서비스 메서드를 지난다.
- 지급·지급취소: `ROLE_ASSET` 권한 행이 직접 있는 사용자만 한다(관리자 거부).
- 신청 상세·목록: 조회 범위는 서비스가 정하며, 화면에서 넘어온 범위 값은 무시한다.
- 신청 내역 내려받기 SQL에는 범위 검사가 없다. 자산담당자 전용 URL 뒤에서만 부른다.

메뉴 노출은 권한과 별개다. 메뉴 조회 SQL은 사용자의 권한 행 1개만 보고 계층을 따르지 않으므로, 역할마다 메뉴를 따로 준다: 신청자는 "비품 신청", 자산담당자는 "비품 신청 + 재고·자산 관리", 관리자는 "비품 신청 + 관리".

## 기본 계정

공통컴포넌트 DML의 기본 계정 `TEST1`, `webmaster`(업무사용자), `USER`(일반회원), `ENTERPRISE`(기업회원)는 공개된 기본 비밀번호가 있다. 초기화 SQL이 세 가지를 모두 한다.
- 잠금 표시를 켠다.
- 권한 행을 지운다.
- 비밀번호를 해시가 될 수 없는 값(`!disabled`)으로 바꾼다.

이 계정들은 관리자 수와 승인자 계산에 들어가지 않는다. 어느 하나라도 되살리면 공개 비밀번호로 로그인되는 계정이 생긴다.

## 이력(감사 대상)

| 사건 | 기록 위치 |
|---|---|
| 재고 수량·확보 수량 변동(입고, 조정, 승인 확보, 지급, 지급 취소 복구) | 재고 이력 — 유형, 증감, 변동 후 값, 사유, 신청번호, 처리자, 시각 |
| 개별 자산 등록·반납·수리·수리 완료·폐기·지급 | 자산 이력 — 이전·이후 상태, 사유, 신청번호, 처리자, 시각 |
| 신청 제출·승인·반려·신청취소·지급·지급취소 | 신청 처리 이력 — 이전·이후 상태, 처리자, 사유, 시각 |
| 부서장 지정 | 지정자와 지정 시각(지정 행에 덮어씀, 해제는 행 삭제) |
| 야간·수동 부족 집계 | 집계 실행 행 + 공통컴포넌트 배치 결과(정상/비정상, 오류 내용) |
| 로그인·접속 | 공통컴포넌트 로그 기능 |
| 데모 암호 적용 | 적용 기록 행(`ASSET_SETUP`) |

이력 행은 화면에서 수정·삭제할 수 없다. 이력 없이 수량·상태를 바꾸는 경로는 없어야 한다.

## 비밀 값 관리

| 값 | 저장 위치 | 생성·적용 | 교체 |
|---|---|---|---|
| DB 앱 계정·암호, MySQL 루트 암호 | `.env` | db 컨테이너가 처음 초기화될 때 계정 생성. app은 기동마다 새 Crypto 키로 암호화해 설정에 기록 | 이미 초기화된 DB의 계정 암호는 `.env`만 바꿔서는 바뀌지 않는다(DB 볼륨 재생성 또는 수동 변경) |
| Crypto 키 | `.env` | 기동마다 키와 짝 해시(Base64 SHA-256)를 설정 파일에 기록. 공개 기본 키 `egovframe`는 거부 | `.env` 변경 후 app 재기동(DB 암호는 새 키로 다시 암호화된다) |
| 데모 암호 | `.env` | 처음 기동할 때 자리표시 값(`!demo-pending`)을 가진 시드 계정에만 한 번 적용하고 적용 기록을 남긴다. 값이 비어 있으면 기동 중단 | 적용 후에는 `.env`를 바꿔도 다시 적용하지 않는다(사용자 화면에서 바꾸거나 DB 재생성) |

- 저장소에는 `.env.example`(키 이름만)만 둔다. 저장소의 설정 파일과 WAR에는 공통컴포넌트의 공개 기본값만 있다.
- 문서·README·로그에는 계정 아이디만 적고 비밀번호·키 값은 적지 않는다.
- 설정 생성 도구는 비밀 값을 출력하지 않는다.
- 기동 로그에 "EgovFramework Fatal ERROR"(기본 Crypto 키 경고)가 나오면 키가 적용되지 않은 것이다.

## CSRF와 입력

- CSRF 보호가 켜져 있다. 모든 POST 폼은 `_csrf` 토큰을 보내야 한다(Spring `form:form` 또는 hidden input). 엑셀 업로드 같은 multipart 폼도 hidden 필드로 보낸다.
- 공통컴포넌트 HTML 태그 필터가 `*.do` 요청 파라미터의 태그를 이스케이프한다. JSP 출력은 `c:out`으로 한다.
- 업로드 확장자와 크기는 공통컴포넌트 설정(`Globals.fileUpload.*`)을 따른다.
