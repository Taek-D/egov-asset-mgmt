# 0004. 비밀 설정은 컨테이너 기동 때 `.env`로 생성

## 배경
- 공통컴포넌트는 DB 암호를 Crypto 키로 암호화해 `globals.properties`에 두고, 키와 짝 해시를 `egov-crypto-config.properties`에 둔다. 기본 키 `egovframe`를 쓰면 기동 로그에 Fatal ERROR가 찍힌다.
- 저장소가 공개되므로 키·암호를 커밋할 수 없고, 검토자는 `docker compose up` 한 번으로 띄워야 한다.

## 결정
- 앱 컨테이너 시작 스크립트는 WAR를 풀고 독립 실행 도구 `ConfigGenerator`를 실행한 뒤 Tomcat을 띄운다.
- `ConfigGenerator`는 `.env`의 키로 두 설정 파일의 해당 줄을 바꿔 `WEB-INF/classes`에 쓴다. DB 암호는 새 키로 암호화해 넣는다.
- 테스트도 같은 도구로 `target/test-classes`에 설정을 만든다.
- 공통컴포넌트의 암호화 설정 방식(암호화된 DB 암호 + 복호화 리졸버)은 그대로 둔다.

## 대안
- **평문 DB 암호로 전환**(`crypto = false`): 공통컴포넌트 표준 방식을 버리게 된다. 사용자가 방식 유지를 택했다.
- **환경 변수를 Spring 플레이스홀더로 직접 주입**: 공통컴포넌트의 `EgovProperties`가 설정 파일을 직접 읽기 때문에 일부 경로에 반영되지 않는다.
- **빌드 때 설정을 구워 넣기**: WAR에 비밀 값이 들어간다.

## 결과
- 앱은 매 기동마다 설정을 새로 만든다. 키를 바꾸면 재기동만으로 DB 암호가 다시 암호화된다.
- 설정 생성 도구가 공통컴포넌트 설정 파일의 줄 형식(`키 = 값`)에 의존한다. 원본에 해당 키가 없으면 실패한다.
- 테스트에서는 `EgovProperties`가 클래스 위치 기준으로 파일을 찾는 문제 때문에 보조 디렉터리가 필요해졌다.
- 데모 암호는 설정 파일이 아니라 DB에 한 번만 적용한다(적용 기록 행). 이후 `.env` 변경은 반영되지 않는다.
