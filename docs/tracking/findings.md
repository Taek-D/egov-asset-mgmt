# 미해결 문제

## 신청서 작성 토큰이 세션당 하나라 두 탭·실패 후 새로고침이 막힘

- 증상:
  - 신청서 작성 화면을 두 탭에 열고 둘 다 제출하면 두 번째 탭은 "이미 제출했거나 만료된 화면입니다"로 거부된다.
  - 제출이 규칙 위반으로 실패한 뒤 새로고침으로 다시 보내도 같은 메시지가 나온다. 작성 화면을 다시 열면 된다.
- 영향: 사용자가 같은 내용을 다시 입력해야 한다. 신청서가 중복으로 생기지는 않는다.
- 지금 못 푸는 이유: 공통컴포넌트 `EgovDoubleSubmitHelper`가 세션에 토큰 하나만 두고 확인 즉시 교체하는 방식이다. 이를 그대로 재사용한 결과라, 바꾸려면 기반 소스를 고치거나 별도 토큰 저장소를 만들어야 한다. 사용자 불편 수준이라 1차 범위에서는 재사용을 택했다.
- 방안: 화면마다 토큰을 발급하는 폼별 토큰 맵을 업무 쪽에 두거나, 실패 응답 때 새 토큰을 담아 다시 그린다.

## 전체 반려의 처리 이력에 사유가 비어 있음

- 증상: 모든 품목을 반려해 신청서가 '반려'가 되면, 신청 처리 이력 행의 사유 칸이 비어 있다. 반려 사유는 품목마다 신청 품목 행에 남는다.
- 영향: 처리 이력만 보는 사람은 반려 이유를 알 수 없다(상세 화면의 품목 목록에는 보인다).
- 지금 못 푸는 이유: 명세가 반려 사유를 품목 단위로 정의하고, 헤더 이력에 무엇을 적을지는 정하지 않았다. 사용자 결정이 필요하다.
- 방안: 반려 품목의 사유를 "품목: 사유" 형식으로 이어 붙여 이력 사유에 넣는다.

## 공통컴포넌트 배치 작업 화면에서 집계 작업 행을 바꿀 수 있음

- 증상:
  - 관리자가 배치 작업 관리 화면에서 `BAT00000000000000001`을 지우면, 이후 집계 결과가 배치 결과 목록에서 보이지 않는다(목록이 작업 테이블과 내부 조인). 집계 자체와 업무 화면은 정상이다.
  - 이 작업에 스케줄을 추가하면 기반 스케줄러가 작업 프로그램을 셸 명령으로 실행하려다 실패 로그를 남긴다.
- 영향: 배치 결과 화면의 감사 기록이 사라지거나 로그가 오염된다.
- 지금 못 푸는 이유: 기반 배치 관리 화면·스케줄러의 동작이다. 막으려면 공통컴포넌트 소스를 고쳐야 한다.
- 방안: 해당 작업 행의 수정·삭제·스케줄 등록을 막는 URL 패턴이나 화면 조건을 추가한다(기반 수정 사유 기록).

## 엑셀 내려받기 파일 이름이 영문

- 증상: 내려받은 파일 이름이 `stock_status.xlsx`처럼 영문이다.
- 영향: 사용 편의만 떨어진다. 내용과 머리글은 한글이다.
- 지금 못 푸는 이유: 실행환경의 `AbstractPOIExcelView`가 `Content-Disposition`의 파일 이름을 인코딩 없이 직접 만든다. 한글 이름을 쓰려면 뷰를 대체해야 한다.
- 방안: RFC 5987(`filename*=UTF-8''...`) 헤더를 쓰는 업무 전용 뷰로 바꾼다.

## 야간 집계 시각 변경이 실제로 시험되지 않음

- 증상: `asset.shortage.cron`·`asset.shortage.zone` 플레이스홀더로 기본값(02:00 Asia/Seoul)을 바꿀 수 있도록 설정은 되어 있으나, 기본값 외의 값으로 기동해 본 적이 없다.
- 영향: 운영자가 시각을 바꿨을 때 반영되지 않을 가능성이 확인되지 않았다.
- 지금 못 푸는 이유: 1차 범위의 검증은 기본값 트리거 계산만 포함했다.
- 방안: 시스템 속성으로 값을 준 기동 테스트를 하나 추가한다.

## 기반 저장소의 GitHub Actions 워크플로 미확인

- 증상: 공통컴포넌트에서 가져온 `.github/workflows/maven.yml`이 그대로 있다. GitHub에 올리면 기반 저장소 기준 빌드가 실행된다.
- 영향: 이 프로젝트 설정(테스트 제외, 업무 테스트용 DB 없음)에서 성공하는지 확인하지 않았다. 실패하면 저장소에 실패 배지·알림이 보인다.
- 지금 못 푸는 이유: 원격 저장소에 올리지 않은 상태라 실행해 볼 수 없다.
- 방안: 올리기 전에 워크플로를 지우거나, `scripts/verify.sh`와 같은 MySQL 서비스 컨테이너를 쓰는 워크플로로 바꾼다.
